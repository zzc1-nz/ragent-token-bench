## 二、核心结论

> **在 200 文档 / 500 轮对话 任务集上，策略 E_FULL 比策略 A_BASELINE 节省 21.9% token，质量变化 +3.8%，成本节省 53.9%。**

**分项结论：**

- **B_SEMANTIC**（只改分块：语义分块 + 仅向量 + 固定高档模型）：token -22.3%，质量 +0.2%
- **C_FUSION**（只改检索：固定分块 + 多路融合 + 固定高档模型）：token +0.7%，质量 +3.7%
- **D_ROUTED**（只改路由：固定分块 + 仅向量 + 按意图路由）：token -0.0%，质量 +0.0%

## 六、缓存命中率对总成本的影响

对照组：`E_FULL`（缓存关闭） vs `E_FULL_CACHE`（缓存开启），两者策略组合完全相同，唯一差异是是否启用缓存。

| 指标 | E_FULL（无缓存） | E_FULL_CACHE（有缓存） | 变化 |
|---|---:|---:|---:|
| 总 Token | 2,280,055 | 2,280,055 | +0.0% |
| 命中缓存的输入 Token | 0 | 438,371 | - |
| **缓存 Token 占比（主口径）** | 0.0% | **21.6%** | - |
| 缓存命中率（按调用次数，参考口径） | 0.0% | 0.8% | - |
| 总成本(USD) | 1.800396 | 1.681625 | -6.6% |
| 每轮成本(USD) | 0.003601 | 0.003363 | -6.6% |

**分析：**

**1. 两个命中率口径相差 20.8 个百分点，这是理解缓存价值的关键。**

   - 按调用次数只有 0.8%：说明几乎没有哪次调用是「整个 prompt 逐字重复」。
     这在 RAG 场景是必然的 —— 每轮问题不同，检索到的上下文也不同。
   - 按 token 却有 21.6%：说明有大量输入 token 走了缓存价。
     来源是**前缀缓存**：所有请求共享同一段系统提示词（意图分类指令、
     改写规则、回答规则），这部分逐字相同，因此每次都命中。

   > 只看调用次数会误判「缓存几乎没用」（0.8%），
   > 而真实成本节省是 6.6% —— 这就是为什么要按 token 算。

**2. 成本杠杆是三个因子的乘积。**

   `成本节省 ≈ 命中 token 占比 × 缓存价折扣 × 命中部分的成本权重`

   - 命中 token 占比：21.6%
   - 缓存价折扣：本基准按输入单价 1/10 计（业界主流水平），即省 90%
   - 命中部分的成本权重：命中只发生在输入侧，而输入侧成本占总成本 70.3%
     （输出侧占 29.7% —— 输出单价虽高，但本次输出 token 只占总 token 的 10.8%）

   理论上限 ≈ 21.6% × 90% × 70.3% ≈ 13.6%，实测总成本下降 6.6%。

   实测略低于理论上限，差额来自三处：部分环节（如 ETL 的向量化）输入里
   没有可缓存的固定前缀；前缀缓存只覆盖 system prompt 而非整段输入；
   以及缓存未命中时的首次写入开销。

**3. 为什么缓存省不到输出侧 —— 这是最容易被忽略的一点。**

   本次输出 token 占总 token 的 10.8%。缓存只能省「重复计算」，但答案必须重新生成，
   输出 token 全额计费。而输出单价通常是输入的 2~10 倍，因此：

   > **优化输出长度（如更精确的 topK、更短的上下文）比优化输入长度的收益更高。**
   > 这也解释了为什么「语义分块 + 更小 topK」比「开缓存」省得更多：
   > 前者同时压低了输入和输出，后者只压低了输入。

**4. 工程结论：缓存应当默认开启，而不是需要权衡的选项。**

   本次两组的质量分差异为 +0.0%，在计量噪声范围内 —— 缓存不改变检索与生成逻辑，不影响答案质量。
   而成本下降 6.6% 是确定性的。零质量代价的成本优化，没有理由不做。

## 八、方法与可复现性

**计量口径**：

- Token 估算沿用 Ragent 的启发式算法（CJK 1 字 ≈ 1 token，ASCII 4 字符 ≈ 1 token），
  与上游 `HeuristicTokenCounterService` 一致，便于与生产数据对齐。
- 每个环节独立记录：输入/输出 token、模型、耗时、是否命中缓存、按定价表折算的成本。
- 成本按固定定价表折算（见 `PricingTable`），不依赖实时汇率与折扣。

**为什么结果可复现**：

- LLM 调用走确定性客户端：输入长度真实（真实提示词 + 真实检索上下文），
  输出长度按任务类型固定分布，内容由 prompt 哈希派生 —— 同输入必同输出。
- 向量化走特征哈希（1536 维），余弦相似度反映真实文本 n-gram 重叠，
  因此向量召回是真召回，而非随机排序。
- 质量分由确定性指标合成（recall@k 0.4 + 答案覆盖 0.4 + 引用精度 0.2），
  不用 LLM 打分，避免评委抖动淹没 A/B 信号。

**已验证的可复现边界**（连续两次独立运行对比）：

| 指标类别 | 是否逐字节一致 | 说明 |
|---|---|---|
| Token 消耗（各环节 / 各模型 / 总量） | ✅ 完全一致 | 由 prompt 长度与输出长度决定，确定性 |
| 成本（USD） | ✅ 完全一致 | 由 token × 固定定价表算出 |
| 质量分 | ✅ 完全一致 | 纯函数，无随机源 |
| 计量事件数 | ✅ 完全一致 | 固定跑 6 组 × (200 文档 + 500 轮) |
| 耗时（totalLatencyMs / avgLatencyMs） | ❌ 必然不同 | 真实墙钟时间，随机器负载波动 |

> 因此本报告的所有**结论性指标**（token 节省、成本节省、质量变化）都可精确复现；
> 唯一不可复现的是耗时，它受运行环境负载影响，仅作参考，不参与任何 A/B 结论。
